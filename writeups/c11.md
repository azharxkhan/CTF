# 11 — Race condition

**The vuln:** the allocation endpoint reads the current count, checks it against the limit,
then writes — with no lock or transaction. Concurrent requests all read the old value before
any of them writes.
```
read count → (gap) → check < limit → write        // TOCTOU: time-of-check to time-of-use
```

**The exploit:** fire many requests at once so they all pass the check, then all allocate.
```bash
seq 1 30 | xargs -P 30 -I{} curl -s -X POST http://<host>:5011/api/allocate >/dev/null
curl -s http://<host>:5011/api/allocate/status      # oversold past the limit → flag
```

**The fix:** make read-check-write atomic — a transaction with proper isolation, an EF
concurrency token (`[Timestamp]` RowVersion), or an atomic `UPDATE ... WHERE stock > 0`.

**The lesson:** correctness under concurrency needs locking, not luck. **`NOLOCK` is the wrong
instinct** — it's `READ UNCOMMITTED` and makes this class of bug worse. The fix is *more*
locking, not less.
