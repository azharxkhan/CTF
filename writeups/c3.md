# 3 — Secret in git history

**The vuln:** a production connection string (with a real password) was committed, then
"removed" in a later commit. The working tree looks clean, but git keeps everything.

**The exploit:** read the history.
```bash
git log --all --oneline                 # spot "Add production configuration"
git show <that commit>                   # the connection string + password
git log -p | grep -i password            # one-shot
```

**The fix (process, not code):**
- **Rotate** the leaked credential — deleting the file does NOT un-leak it; anyone with the
  history already has it.
- Move secrets to environment variables / `dotnet user-secrets` / a secrets store.
- `.gitignore` the config file from commit one.
- (Bonus) purge it from history with `git filter-repo` / BFG — but rotation is what stops the leak.

**The lesson:** a committed secret is compromised the moment it's pushed. Rotate, don't just delete.
